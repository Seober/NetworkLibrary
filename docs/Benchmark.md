# 벤치마크 가이드

`TestServer` + `TestClient`로 네트워크 라이브러리의 성능 지표를 측정하고, 리팩토링 전후를 정량 비교하기 위한 하네스 사용법.

- 설정: `Examples/BenchmarkConfig.ini` (빌드 시 실행 파일 폴더로 복사됨)
- 결과: 실행 파일 폴더의 `Benchmark\` 아래 CSV
- 관련 코드: `Examples/TestServer/main.cpp`, `Examples/TestClient/main.cpp`, `BaseLibrary/include/Config.h`, `BaseLibrary/include/Statistics.h`

---

## 1. 무엇을 재는가

`TestServer`는 받은 패킷을 그대로 돌려주는 순수 에코 서버, `TestClient`는 N개 세션을 붙여 일정 간격으로 패킷을 보내고 **에코가 정확히 돌아왔는지 검증**한다. 양쪽이 각자 독립적으로 초당 지표를 기록하고, 종료 시 통계 구간을 잘라 요약 한 줄을 남긴다.

측정 목적은 **절대 성능이 아니라 회귀 탐지**다. 같은 머신에서 같은 설정으로 돌렸을 때 수치가 흔들리면 그 사이의 변경을 의심한다.

> **서버와 클라이언트가 같은 머신에서 돈다.** loopback 합산 부하라서 클라이언트가 쓰는 CPU가 서버 수치에 섞인다. **동일 머신·동일 조건 내 비교만 유효**하고, 다른 머신의 수치나 공개 벤치마크와 비교하는 용도로는 쓸 수 없다.

### 1.1 부하 조건이 바뀐 경계 (커밋 `4bb299c`)

**이 커밋을 기준으로 측정값이 단절된다. 경계를 넘는 비교는 성립하지 않는다.**

| | `4bb299c` 이전 | 이후 (현재) |
|---|---|---|
| 타이머 해상도 | OS 기본 (약 15.6ms) | **1ms** (`timeBeginPeriod`) |
| 송신 스윕 주기 | 31.2ms (= 15.6 × 2) | **19.1ms** |
| 세션당 초당 송신 | 32~33회 | **52~53회** |
| `RecvTPS_p50` | 65,975 | **104,000** |
| 서버 `Cpu_avg` | 15.0% | **19.9~20.7%** |
| 샘플 주기 편향 | 1.8% | **0.84%** |

이전 부하는 Windows 타이머 분해능에 묶여 있어 라이브러리를 거의 누르지 못했다. 자세한 경위는 [12.2](#122-이전-부하-조건-4bb299c-이전)에 남긴다. **이 문서의 수치는 따로 표기하지 않는 한 전부 현재 조건 기준이다.**

> 같은 날의 후속 커밋 `785e40c`(스로틀링 opt-out)·`9c69c75`(`RecvTotal` 추가)는 **측정값을 바꾸지 않는다.** 비교 경계는 `4bb299c` 하나뿐이므로, 그 이후 런끼리는 커밋이 달라도 비교할 수 있다.

## 2. 실행 방법

### 2.1 설정 파일 위치

빌드 후처리(`xcopy /Y /D`)가 `Examples\BenchmarkConfig.ini`를 실행 파일 폴더로 복사한다. **`/D`는 원본이 더 최신일 때만 덮어쓴다.**

- **일회성 조건 변경**: 실행 파일 폴더의 ini를 직접 수정한다. 수정본이 더 최신이 되므로 리빌드해도 덮어쓰이지 않고, 리빌드 자체가 불필요하다.
- **기본값 영구 변경**: `Examples\BenchmarkConfig.ini`를 고치고 리빌드한다.

`argv[1]`로 다른 경로를 넘길 수도 있다 (프로젝트 속성 → 디버깅 → 명령 인수, 또는 바로 가기 속성). 단 **상대 경로는 작업 디렉터리(`$(ProjectDir)`) 기준**이라 exe 폴더가 아니다.

### 2.2 순서

1. **무거운 프로그램은 닫아 두는 편이 좋다.** 다만 이것으로 측정이 깨끗해진다는 보장은 없다 — [10장](#10-저속-구간-현상-원인-미상) 참고.
2. **`TestServer` 먼저** 실행. 콘솔 머리에 찍히는 설정이 의도한 값인지 확인한다.
3. **`TestClient`** 실행. 서버는 `IdleTimeout` 안에 접속이 없으면 `INVALID(no connection)`으로 중단하므로 그 안에 띄운다.

**둘 다 Ctrl+F5(디버깅하지 않고 시작)로 실행할 것.** 디버거를 붙이면
- 종료 시 콘솔이 즉시 닫혀 Result 블록을 못 본다 ("아무 키나 누르세요"는 디버그 세션 전체가 끝날 때만 표시되므로, 먼저 끝나는 쪽은 그냥 사라진다),
- 예외를 디버거가 먼저 가로채 `MyExceptionFilter`가 실행되지 않아 덤프가 안 생기며,
- 디버그 힙·예외 처리 오버헤드가 수치에 섞인다.

### 2.3 창을 내려도 된다

Windows 11은 창이 최소화되거나 완전히 가려진 프로세스의 타이머 해상도 요청을 기본적으로 무시한다. 두 프로그램 모두 시작 시 `SetProcessInformation`으로 그 스로틀링을 명시적으로 해제하므로 **창 상태와 무관하게 1ms가 유지된다.**

해제에 실패하면 콘솔에 아래가 찍힌다. **이 줄이 보이면 측정 중 창을 내리지 말 것.**

```
[TimerRes] warning: throttling opt-out failed (err N) - keep the console window visible
```

### 2.4 종료

| | 종료 조건 |
|---|---|
| TestClient | `Minutes + Trim × 2`분 경과 시 자동 종료 (`Minutes=0`이면 무제한) |
| TestServer | 접속이 0인 상태가 `IdleTimeout`분 지속되면 종료 |

양쪽 모두 `Q` 키로 즉시 중단할 수 있다. 중단한 런은 통계 구간이 짧아 `INVALID(window too short)`로 기록된다.

서버에는 `(Minutes + Trim×2)×60 + IdleTimeout×60 + 300`초의 안전 상한이 걸려 있다. 여기 걸리면 `INVALID(max duration)`이며, 무언가 멈춘 것이다. 무제한 모드에서는 해제된다.

## 3. 티어

| 티어 | `Minutes` | `Trim` | 클라 실행 | 서버 종료까지 | 용도 |
|---|---|---|---|---|---|
| smoke | 5 | 1 | 7분 | 약 12분 | 하네스 동작·CSV 포맷 확인 전용. **비교 대상 아님** |
| 기본 | 30 | 5 | 40분 | 약 45분 | 표준 비교 단위 |
| 확장 | 60 | 5 | 70분 | 약 75분 | 메모리 추세 확인 |
| 무제한 | 0 | 5 | `Q`까지 | `Q` 후 유휴 | 장기 관찰·수동 실험 |

**smoke를 비교에 쓰면 안 되는 이유**는 **블록 교차 확인을 할 수 없기 때문**이다. 5분 런은 샘플이 1/6이고 trim이 1분뿐이라, 구간을 쪼개 서로 대조할 블록이 나오지 않는다.

**블록 교차 확인** — 통계 구간을 5분 블록으로 나눠 **`p95`를 비교**한다. 실측으로 30분 런 2건의 블록 `p95`는 각각 **0.74% / 1.04%** 안에서 일치했다. 블록 하나만 처지면 그 시간대에 간섭이 있었던 것이고, 전 블록이 고르게 낮으면 런 전체가 이상했던 것이다.

> **블록 `p50`은 쓸 수 없다.** 2026-10-20 정리환경 런의 블록 `p50`은 77,792 ~ 105,187로 **35% 널뛰었다.** [10장](#10-저속-구간-현상-원인-미상)의 현상 때문에 블록마다 중앙값이 두 모드 중 어디에 걸리는지가 달라지기 때문이다. 같은 런의 블록 `p95`는 106,000 ~ 107,104로 안정적이었다.

**무제한 모드**에서는 `Q`를 누른 시점이 트래픽 종료로 잡히고, 거기서 앞뒤 `Trim`분을 잘라낸 구간이 통계가 된다.

## 4. 설정 키

전체 주석은 `BenchmarkConfig.ini` 안에 있다. 여기서는 헷갈리기 쉬운 것만 다룬다.

### `[Analysis]`

```ini
Minutes = 30   ; 통계를 낼 구간 길이
Trim    = 5    ; 트래픽 시작 직후 / 종료 직전 제외 구간
```

통계 구간 = **트래픽 구간에서 앞뒤 `Trim`분을 뺀 나머지**다. 접속 ramp, 메모리풀 성장, 종료 구간을 평균에서 배제한다. 클라이언트가 끊긴 뒤 서버가 `IdleTimeout`을 세는 유휴 구간은 트래픽 구간 밖이므로 정의상 자동으로 빠진다.

`Trim × 2 >= Minutes`이면 설정 오류로 중단한다.

### `[Server] NagleEnabled`

**Nagle 알고리즘**은 작은 송신을 모아서 한 번에 보내는 TCP 최적화다. 대역폭에는 유리하지만 지연이 늘어난다. 이를 끄는 소켓 옵션이 `TCP_NODELAY`라서 **이름과 동작이 서로 반대**라 늘 헷갈린다.

| ini | TCP_NODELAY | 동작 |
|---|---|---|
| `NagleEnabled = true` | FALSE | 패킷을 모아서 전송. 대역폭 유리, 지연 증가 |
| `NagleEnabled = false` | TRUE | 즉시 전송. 지연 최소, 패킷 수 증가 |

ini는 **"Nagle을 켤 것인가"**를 묻는다. baseline은 `false`(즉시 전송)다.

> 참고: `NetServer::Start`의 `nagle` 인자는 실제로는 `TCP_NODELAY` 값이라 의미가 반대다. `main.cpp`에서 `BOOL noDelay = nagleEnabled ? FALSE : TRUE;`로 뒤집어 넘긴다. 인자명 정리는 별도 과제.

### `[Client] Mode`

- `Mode = 1` — 접속을 끝까지 유지. `LifetimeMin/Max`, `ReconnectMin/Max`는 **무시**되며, 0이 아니면 경고를 출력한다(중단은 아님).
- `Mode = 2` — 일정 시간 유지 후 끊고 재접속 반복. `Server.IdleTimeout`이 `Client.ReconnectMax`보다 커야 한다. 안 그러면 재접속 공백을 서버가 "트래픽 종료"로 오판한다.

### `[Client] SendIntervalMin / Max` — 현재 효과가 없다

세션당 송신 간격(ms)으로 설계됐으나, **현재 설정 범위에서는 동작하지 않는다.** 송신 스윕 주기가 약 19ms라 1~5ms 간격은 매 스윕마다 항상 만족된다. 자세한 내용은 [9.2](#92-부하-노브가-동작하지-않는다). 부하를 실제로 바꾸려면 `SenderThread`의 `Sleep(10)`을 고쳐야 한다.

### 서버·클라가 ini 한 파일을 공유한다

두 프로그램 모두 `[Server]`·`[Client]` **전 키를 읽는다.** 읽지 않은 키가 남으면 오타로 간주해 중단하기 때문이다. 키 하나를 추가하면 양쪽 `main.cpp`에서 모두 읽어야 한다.

### 설정 오류는 조용히 넘어가지 않는다

`Config`는 아래를 모두 **중단 사유**로 처리한다. 잘못된 조건으로 45분을 날리는 것보다 즉시 멈추는 게 낫다.

| 분류 | 예 |
|---|---|
| 파싱 | 섹션 미종료, 빈 섹션명, `=` 누락, 섹션 밖의 키, 빈 키, 빈 값, **중복 키** |
| 타입 | 정수가 아님, boolean이 아님(`true`/`false`/`1`/`0`만 허용) |
| 누락 | 필수 키 없음 (`missing required key`) |
| 오타 | 아무도 읽지 않은 키 (`unknown key(s) - check for typo`) |
| 값 검증 | `Trim×2 >= Minutes`, `MaxUser < ClientCount`, `Server.Port != Client.ServerPort` |

기본값으로 대체된 키는 요약 CSV의 `DefaultedKeys` 컬럼에 남는다. **baseline 런에서는 이 칸이 비어 있어야 한다.**

## 5. 결과 파일

```
Benchmark\
├─ {Label}_{YYYYMMDD}_{HHMMSS}_server_samples.csv   런마다 새 파일
├─ {Label}_{YYYYMMDD}_{HHMMSS}_client_samples.csv   런마다 새 파일
├─ server_summary.csv                               런마다 한 줄씩 append
└─ client_summary.csv                               런마다 한 줄씩 append
```

모두 UTF-8 BOM + 한글 병기 헤더라 Excel에서 바로 열린다.

### 5.1 샘플 CSV — 초당 1행

| 컬럼 | 의미 |
|---|---|
| `Timestamp`, `ElapsedSec` | 시각, 시작 후 경과 초 |
| `Connected` | 현재 접속 수 |
| `FreeSession` *(서버)* | 세션 풀 여유분. 고갈되면 접속 실패 |
| `ConnectTotal`, `DisconnectTotal` *(클라)* | 누적 접속·끊김 |
| `RecvTPS`, `SendTPS` | **샘플 구간의** 패킷 수 |
| `RecvBytes`, `SendBytes` | **샘플 구간의** 바이트 수 (TCP/IP 헤더 40B 포함 추정치) |
| `AcceptTPS` *(서버)* | **샘플 구간의** accept 수 |
| `RecvTotal` *(클라)* | 수신한 **누적** 패킷 수 |
| `VerifiedTotal` *(클라)* | 에코 내용까지 검증한 **누적** 패킷 수 |
| `PoolTotal`, `PoolUse`, `PoolFree` | 패킷 풀 전체/사용/여유 |
| `CpuProcess` | **이 프로세스**의 CPU (코어 수로 나눈 값. 12코어에서 100%면 전 코어 포화) |
| `CpuProcessor` | **머신 전체** CPU |
| `MemProcessMB` | 이 프로세스의 `Private Bytes` (MB, 소수점 1자리) |

> **`*TPS`·`*Bytes`는 구간 속도, `*Total`은 누계 스냅샷이다.** 성질이 다르므로 **속도 컬럼을 합산해 누계와 비교하면 안 된다** — 샘플링 루프가 두 값을 읽는 시점이 미세하게 달라 런 끝에서 수백 개가 어긋나고, 이는 유실이 아니다.
>
> **정합성은 `RecvTotal`과 `VerifiedTotal`을 직접 비교한다.** 두 카운터는 `OnRecv` 안에서 나란히 증가하므로 항상 같아야 하고, 다르면 패킷 타입 불일치다.

### 5.2 요약 CSV — 런당 1행

`Label` / `StartTime` / `Valid` / `Cfg*`(재현에 필요한 설정) / 통계 / 자원 사용 / `DefaultedKeys` 순. 런을 거듭하며 **같은 파일에 누적**되므로 그대로 열어 행끼리 비교하면 된다.

> **컬럼 구성을 바꾸면 기존 파일을 `client_summary_v1.csv` 식으로 rename하고 새로 시작할 것.** append 방식이라 헤더가 섞이면 Excel에서 열이 어긋난다.

## 6. 수치 읽는 법

### 6.1 백분위 (p5 / p50 / p95)

백분위는 **평균이 아니라 정렬했을 때의 위치값**이다. 초당 샘플을 전부 정렬한 뒤 nearest-rank(`index = ceil(p × N) - 1`)로 뽑는다.

- `p50` — 중앙값. 샘플의 절반이 이 값 이상
- `p95` — 상위 5% 경계. 전체의 5%만 이보다 높음
- `p5` — 하위 5% 경계. 전체의 5%만 이보다 낮음

**처리량은 지연 시간과 방향이 반대다.** 지연은 p95가 "최악의 경우"지만, **처리량은 p95가 "가장 잘 나온 초"**이고 **p5가 "가장 안 나온 초"**다.

### 6.2 회귀 비교 지표

처리량 분포가 두 모드로 갈려 있어([10장](#10-저속-구간-현상-원인-미상)) **평균과 중앙값은 두 모드의 혼합 비율에 끌려다닌다.** 비율은 런마다 달라지므로 비교에 쓸 수 없다.

2026-10-20에 저속 비율이 **23.6% → 46.0%**로 2배 가까이 널뛴 4개 런에서:

| 지표 | 변동폭 | 비교 사용 |
|---|---|---|
| **`RecvTPS_p95`** | **0.5%** | ✅ 부하 상한 |
| **`Cpu_p25`** | **0.6%** | ✅ 처리 비용 |
| `RecvTPS_p50` | 4.3% | ❌ |
| `Cpu_avg` | 8.9% | ❌ |
| `RecvTPS_avg` | 7% | ❌ |

`Cpu_avg`와 저속 비율의 상관계수는 **+0.996**이었다. 즉 `Cpu_avg`는 사실상 "저속 비율을 재는 지표"이지 처리 비용이 아니다. 반면 `Cpu_p25`의 상관계수는 **−0.136**으로 무관하다.

| 변화 | 해석 |
|---|---|
| `RecvTPS_p95`가 떨어짐 | **상한 자체가 낮아짐.** 라이브러리 회귀를 의심할 1순위 신호 |
| `Cpu_p25`가 오름 | 같은 부하를 처리하는 비용이 늘어남. **핫패스 회귀의 주 신호** |
| 둘 다 그대로, `Cpu_avg`만 오름 | 저속 비율이 올라간 것. 라이브러리와 무관 |

> **`Cpu_p25`는 요약 CSV에 컬럼이 없다.** 샘플 CSV에 초당 데이터가 전부 남으므로 비교 시 계산한다. 블록 단위(5분, 약 300샘플)로는 변동이 4~9%로 커지므로 **런 단위로만 쓴다.**

### 6.3 `CpuProcessor_avg`는 더 이상 유효성 판정에 쓸 수 없다

과거 "정상 42~46% / 경합 55% / 높으면 폐기" 규칙을 썼으나, **현재 부하에서는 정상 런도 51~52%로 올라가** 변별력이 없다. 게다가 [10장](#10-저속-구간-현상-원인-미상)의 저속 구간에서는 머신 CPU가 61.5%까지 오르는데, 이는 외부 경합과 구분되지 않는다.

**대신 유효성은 `RecvTPS_p95`·`Cpu_p25`의 재현성과 [7장](#7-런-유효성-체크리스트)의 항목으로 판단한다.** `CpuProcessor_avg`는 기록만 하고 참고용으로 본다.

## 7. 런 유효성 체크리스트

요약 CSV의 새 행을 믿기 전에 확인한다.

1. **`Valid` = `OK`** — 아래 값은 모두 폐기 대상이다.

   | 값 | 뜻 |
   |---|---|
   | `INVALID(no connection)` | `IdleTimeout` 안에 아무도 접속하지 않음 |
   | `INVALID(window too short)` | 통계 구간이 비었음. `Q`로 일찍 중단한 경우 포함 |
   | `INVALID(max duration)` | 안전 상한 도달. 무언가 멈춤 |

   `INVALID` 행은 `WindowEndSec`가 음수로 찍힐 수 있다. 정상이며 무시하면 된다.

2. **`DefaultedKeys`가 비어 있을 것** — 비어 있지 않으면 ini의 키 이름이 깨졌거나 누락된 것이다.

3. **`WindowSamples`가 구간 길이와 맞을 것** — 30분 구간이면 1780~1800 정도. 약 0.8% 모자란 것은 정상이다([9.1](#91-샘플-주기는-1초가-아니라-약-1008초)). 크게 모자라면 샘플러가 굶은 것이다.

4. **`Connected_min`이 설정한 `ClientCount`와 같을 것** (Mode 1) — 중간에 끊긴 세션이 있으면 작아진다.

5. **`RecvTotal` == `VerifiedTotal`** (클라) — 다르면 패킷 타입 불일치다.

6. **`RecvTPS_p95`가 baseline과 1% 이내일 것** — 크게 벗어나면 런 자체가 이상했거나 실제 회귀다. 블록 교차 확인([3장](#3-티어))으로 어느 쪽인지 가른다.

7. **행이 아예 없으면 크래시다.** 주기적 flush를 하지 않으므로 정상 종료 때만 기록된다. 이때는 실행 파일 폴더의 `Dump_*.dmp`를 확인한다.

## 8. 메모리와 풀 판독

### 8.1 `Mem_slopeMBperHour`의 해상도 한계

메모리는 0.1MB 단위로 기록된다. 짧은 구간에서는 **기록 해상도 자체가 시간당으로 증폭**된다.

| 구간 | 0.1MB가 환산되는 값 | 유의미한 최소 기울기 |
|---|---|---|
| 5분 | 1.2 MB/h | 읽지 말 것 |
| 30분 | 0.2 MB/h | 약 2 MB/h 이상 |
| 60분 | 0.1 MB/h | 약 1 MB/h 이상 |

누수 판단은 **확장(60분) 티어에서, 여러 런의 추세로** 한다. 30분 런 하나의 기울기로 단정하지 않는다.

### 8.2 서버 메모리는 부하가 아니라 `MaxUser`에 비례한다

`Session` 하나가 `SendBuffer[1000]`(포인터 8KB) + `RecvQ{4096}`을 들고 있어 약 13KB다. 서버는 이를 **`MaxUser`개만큼 시작 시 선할당**한다.

```
MaxUser 32000 × 약 13KB = 약 416MB
```

baseline 런의 서버 메모리 425MB가 여기서 나온다. 클라이언트는 `ClientCount`(2000)만 잡으므로(약 26MB + 프로세스 기본 사용량) 40MB 수준이다. **`MaxUser`가 다른 런끼리 메모리를 비교하는 것은 의미가 없다.**

### 8.3 패킷 풀

`Pool_end`(종료 시 풀 크기)가 **런을 거듭하며 계속 커지면** 패킷 반납 누락을 의심한다. 한 런 안에서 `Pool_max`까지 커졌다가 `Pool_end`로 줄어드는 것은 정상이다 — 피크 부하에 맞춰 풀이 자라고, 반납된 노드가 여유분으로 남는 구조다.

## 9. 측정 특성

하네스 자체의 성질. 결함이 아니라 **알고 읽어야 하는 것**들이다.

### 9.1 샘플 주기는 1초가 아니라 약 1.008초

`NetServer::GetTransmit` / `NetClient::GetTransmit`은 `exchange(0)`으로 **읽으면서 리셋하는 누적 카운터**다. 반환값은 "직전 호출 이후의 개수"이지 초당 비율이 아니며, **시간축은 호출하는 쪽의 책임**이다.

측정 루프는 `Sleep(1000)` + PDH 갱신 + `printf`로 구성되어 실제 주기가 **약 1.0084초**다. 따라서 CSV의 `RecvTPS`/`SendTPS`/`RecvBytes`/`SendBytes`/`AcceptTPS`는 **참값보다 약 0.84% 높다.**

참 처리량은 `구간 패킷 합 / 구간 벽시계 초`로 구한다.

> **왜 보정하지 않는가**: 이 편향은 같은 머신·같은 빌드에서 상수이므로 런끼리 비교에는 영향이 없다. 다만 `printf`와 PDH 소요 시간에 좌우되므로 **다른 머신이나 다른 빌드 구성의 절대값과 비교할 때는 성립하지 않는다.** 보정하려면 샘플마다 실측 경과 시간으로 나눠야 하고, 이때 `GetTickCount`(분해능 15.6ms)는 쓸 수 없다 — `std::chrono::steady_clock`을 써야 한다.

### 9.2 부하 노브가 동작하지 않는다

`SenderThread`는 전 세션을 한 번 훑고 `Sleep(10)`을 호출한다. 실측 스윕 주기는 **약 19.1ms**(`Sleep` 약 10ms + 2000세션 스윕 약 9ms)이고, 세션당 송신은 **초당 52~53회**로 양자화된다.

`SendIntervalMin/Max = 1~5ms`는 스윕 주기보다 훨씬 짧아 **모든 세션이 매 스윕마다 항상 송신 조건을 만족**한다. 즉 이 설정은 무시된다. 부하를 실제로 바꾸려면 `Sleep(10)` 값을 고쳐야 한다.

| `Sleep` | 스윕 주기 | 세션당/초 | 추정 TPS |
|---|---|---|---|
| 10 (현재) | 19.1ms | 52 | 104k |
| 5 | 약 14ms | 71 | 143k |
| 0 | 약 9ms | 111 | 222k |

### 9.3 다음 병목은 `SenderThread`다

실측 스윕 주기 19.1ms에서 `Sleep(10)`이 약 10ms를 차지하므로, 2000세션 순회에 **약 9ms가 쓰이는 것으로 추정**된다(직접 계측하지 않았다). 그렇다면 단일 스레드가 **약 47% 사용률**이므로, 부하를 더 올리면 라이브러리보다 부하 생성기가 먼저 한계에 닿는다.

**부하를 올리는 것은 권장하지 않는다.** 머신 CPU가 이미 51%이고 서버·클라가 거의 반씩 쓰고 있다. 더 밀어붙이면 [10장](#10-저속-구간-현상-원인-미상)의 저속 비율이 올라가 "같은 부하를 반복 적용한다"는 전제가 무너진다. 포화 시험은 **서버와 클라를 다른 머신에 두는 단계**에서 한다.

### 9.4 누계 카운터는 64비트다

`ConnectCnt`·`DisconnectCnt`·`RecvCnt`·`VerifiedCnt`는 `std::atomic<long long>`이다. `int`였다면 104k/s에서 약 5.7시간에 오버플로되어 무제한 모드 장기 관찰에서 정합성 검사가 조용히 무의미해졌을 것이다.

## 10. 저속 구간 현상 (원인 미상)

### 10.1 무엇인가

통계 구간의 초당 샘플이 **두 모드로 갈린다.** (아래 수치는 균형 30분 런 기준)

| | 정상 | **저속** |
|---|---|---|
| 세션당 초당 송신 | 51.6회 | **39.3회** (−24%) |
| 서버 CPU | 16.9% | **25.5%** (+51%) |
| 클라 CPU | 19.0% | **28.3%** (+49%) |
| 머신 CPU | 45.5% | **61.5%** |

**일은 덜 하는데 CPU는 더 쓴다.** 패킷당 처리 비용이 약 2배가 된다. 서버와 클라이언트가 **동시에** 같은 방향으로 움직인다(두 프로세스 CPU 상관계수 **+0.766**).

구간의 길이와 빈도는 런마다 다르다.

| 런 | 저속 비율 | 구간 횟수 | 길이 중앙값 | 최대 |
|---|---|---|---|---|
| 균형 30분 | 34.2% | 119회 | 2초 | 34초 |
| 정리 30분 | 46.0% | 20회 | 30초 | 109초 |

### 10.2 배제한 원인

| 후보 | 배제 근거 |
|---|---|
| 라이브러리 코드 | 서버·클라가 **동시에** 열화 (상관계수 +0.766). 코드 문제면 한쪽만 |
| 서버 처리 지연 | `Recv − Send = 0`. 백로그 없음 |
| 패킷 풀 고갈 | `PoolTotal`·`PoolUse`·`PoolFree` 저속/정상 구간 동일 |
| 메모리·세션 문제 | 메모리 평탄, `Connected` 2000 유지 |
| 일시적 외부 간섭 | 30분 내내 분포. 5분 블록 전부에 존재 |
| **전원 관리(주파수 스케일링)** | 고성능 구성표로 전환 후에도 **40.4%** — 개선 없음 |
| **사용자 배경 프로세스** | 정리 후에도 **46.0%** — 개선 없음 |

### 10.3 모르는 것

원인을 특정하지 못했다. 남은 가설은 **열·전력 한계**, **스케줄러·코어 거동**, **OS 주기 작업** 정도이며, 가르려면 CPU 클럭·온도를 초 단위로 로깅해 저속 구간과 겹쳐 봐야 한다.

"같은 일에 CPU 시간이 더 든다"는 패턴은 **CPU 클럭이 떨어질 때** 전형적으로 나타나지만, 고성능 구성표가 효과가 없었으므로 **단순한 형태의 주파수 스케일링은 아니다.** 이 이상은 가설이다.

**추적은 중단한다.** 투입 대비 얻는 것이 적고, 서버·클라를 다른 머신으로 분리하면 성질이 달라질 문제다. 그 단계에서 재확인한다.

### 10.4 그래도 측정은 유효하다

| 확인 항목 | 결과 |
|---|---|
| 패킷 유실 | **0** — `RecvTotal` == `VerifiedTotal` |
| 세션 끊김 | **0** |
| 메모리 누수 | 없음 |
| 패킷 풀 | 정상 |

**데이터는 전부 정확하다. 처리 속도가 들쭉날쭉했을 뿐이다.** 그리고 [6.2](#62-회귀-비교-지표)의 두 지표는 저속 비율이 2배 널뛰는 동안 0.5% 안에서 재현됐다. **지표만 바르게 고르면 이 현상과 무관하게 비교할 수 있다.**

## 11. 운용 지침

1. **조건을 바꾸면 `Label`을 바꾼다.** 요약 CSV에서 행을 구분하는 유일한 수단이다.
2. **3회 돌려 `RecvTPS_p95`와 `Cpu_p25`의 중앙값을 비교한다.** 1회 수치로 몇 % 차이를 논하지 않는다.
3. **비교 대상은 같은 티어끼리.** smoke 수치는 기본·확장 티어와 비교하지 않는다.
4. **커밋 `4bb299c` 경계를 넘는 비교는 하지 않는다**([1.1](#11-부하-조건이-바뀐-경계-커밋-4bb299c)).
5. **리팩토링 전후 비교 순서** — 변경 전 기본 티어 3회 → 변경 → 3회. 중앙값으로 `RecvTPS_p95`와 `Cpu_p25`를 본다.
6. **전원 관리를 고성능으로 바꿀 이유가 없다.** 바꿔도 측정이 개선되지 않음을 확인했으므로([10.2](#102-배제한-원인)), 발열·소음을 감수할 근거가 없다. baseline은 균형 조정에서 측정했다.
7. **`Benchmark\`는 `.gitignore` 대상이다.** 보존할 결과는 별도로 옮긴다.

### 12.2 이전 부하 조건 (`4bb299c` 이전)

**2026-10-16, 30분, OS 기본 타이머(약 15.6ms).** `RecvTPS_p50` 65,975 / 서버 `Cpu_avg` 15.0% / `CpuProcessor_avg` 42.4%. 서버·클라 측정이 0.002% 내로 일치했고 정합성 100%였다.

이 조건에서는 송신이 15.6ms 타이머 틱에 고정되어 **세션당 송신이 정확히 32~33회로 양자화**됐고, 서버 CPU가 15%로 라이브러리가 포화와 거리가 멀었다. 부하가 타이머에 묶여 변동이 없었던 덕에 수치는 매우 안정적이었지만, **라이브러리를 거의 누르지 못하는 측정이었다.**

**현재 조건 대비 p50 +57.6%, 패킷당 CPU 비용 −16%.** 두 조건의 수치는 비교 대상이 아니다.
