# 벤치마크 가이드

`TestServer` + `TestClient`로 네트워크 라이브러리의 성능 지표를 측정하고, 리팩토링 전후를 정량 비교하기 위한 하네스 사용법.

- 설정: `Examples/BenchmarkConfig.ini` (빌드 시 실행 파일 폴더로 복사됨)
- 결과: 실행 파일 폴더의 `Benchmark\` 아래 CSV
- 관련 코드: `Examples/TestServer/main.cpp`, `Examples/TestClient/main.cpp`, `BaseLibrary/include/Config.h`, `BaseLibrary/include/Statistics.h`

---

## 1. 무엇을 재는가

`TestServer`는 받은 패킷을 그대로 돌려주는 순수 에코 서버, `TestClient`는 N개 세션을 붙여 일정 간격으로 패킷을 보내고 **에코가 정확히 돌아왔는지 검증**한다. 양쪽이 각자 독립적으로 초당 지표를 기록하고, 종료 시 통계 구간을 잘라 요약 한 줄을 남긴다.

측정 목적은 **절대 성능이 아니라 회귀 탐지**다. 같은 머신에서 같은 설정으로 돌렸을 때 수치가 흔들리면 그 사이의 변경을 의심한다.

> **중요 — 서버와 클라이언트가 같은 머신에서 돈다.** loopback 합산 부하라서 클라이언트가 쓰는 CPU가 서버 수치에 섞인다. 따라서 **동일 머신·동일 조건 내 비교만 유효**하고, 다른 머신의 수치나 공개 벤치마크와 비교하는 용도로는 쓸 수 없다.

---

## 2. 실행 방법

### 2.1 설정 파일 위치

빌드 후처리(`xcopy /Y /D`)가 `Examples\BenchmarkConfig.ini`를 실행 파일 폴더로 복사한다. **`/D`는 원본이 더 최신일 때만 덮어쓴다.**

- **일회성 조건 변경**: 실행 파일 폴더의 ini를 직접 수정한다. 수정본이 더 최신이 되므로 리빌드해도 덮어쓰이지 않고, 리빌드 자체가 불필요하다.
- **기본값 영구 변경**: `Examples\BenchmarkConfig.ini`를 고치고 리빌드한다.

`argv[1]`로 다른 경로를 넘길 수도 있다 (프로젝트 속성 → 디버깅 → 명령 인수, 또는 바로 가기 속성).

### 2.2 순서

1. **머신을 조용하게** 만든다. 다른 프로세스가 돌면 `CpuProcessor_avg`가 올라가고 측정이 무효가 된다.
2. **`TestServer` 먼저** 실행. 콘솔 머리에 찍히는 설정이 의도한 값인지 확인한다.
3. **`TestClient`** 실행. 서버는 `IdleTimeout` 안에 접속이 없으면 `INVALID(no connection)`으로 중단하므로 그 안에 띄운다.

**둘 다 Ctrl+F5(디버깅하지 않고 시작)로 실행할 것.** 디버거를 붙이면
- 종료 시 콘솔이 즉시 닫혀 Result 블록을 못 본다 ("아무 키나 누르세요"는 디버그 세션 전체가 끝날 때만 표시되므로, 먼저 끝나는 쪽은 그냥 사라진다),
- 예외를 디버거가 먼저 가로채 `MyExceptionFilter`가 실행되지 않아 덤프가 안 생기며,
- 디버그 힙·예외 처리 오버헤드가 수치에 섞인다.

### 2.3 종료

| | 종료 조건 |
|---|---|
| TestClient | `Minutes + Trim × 2`분 경과 시 자동 종료 (`Minutes=0`이면 무제한) |
| TestServer | 접속이 0인 상태가 `IdleTimeout`분 지속되면 종료 |

양쪽 모두 `Q` 키로 즉시 중단할 수 있다. 중단한 런은 통계 구간이 짧아 `INVALID(window too short)`로 기록된다.

서버에는 `(Minutes + Trim×2)×60 + IdleTimeout×60 + 300`초의 안전 상한이 걸려 있다. 여기 걸리면 `INVALID(max duration)`이며, 무언가 멈춘 것이다. 무제한 모드에서는 해제된다.

## 3. 티어

| 티어 | `Minutes` | `Trim` | 클라 실행 | 서버 종료까지 | 용도 |
|---|---|---|---|---|---|
| smoke | 5 | 1 | 7분 | 약 12분 | 하네스 동작 확인 전용. **비교 대상 아님** |
| 기본 | 30 | 5 | 40분 | 약 45분 | 표준 비교 단위 |
| 확장 | 60 | 5 | 70분 | 약 75분 | 메모리 추세 확인 |
| 무제한 | 0 | 5 | `Q`까지 | `Q` 후 유휴 | 장기 관찰·수동 실험 |

**smoke를 비교에 쓰면 안 되는 이유**는 수치가 더 흔들려서가 아니다. 실제로 기본 티어의 p50은 대단히 안정적이다 — baseline 런의 통계 구간을 5분 블록 6개로 쪼개 보면 p50이 65973~65980으로 **0.01% 안에 들어온다.**

문제는 **경합을 알아챌 방법이 없다**는 것이다. 5분 런은 샘플이 1/6이고 trim이 1분뿐이라, 머신이 간섭받은 런과 조용한 런을 구분할 내부 근거가 없다. 실제로 2026-08-12 smoke 런은 **5분 내내 균일하게** 낮았고(분당 p50 53980~58485, 머신 CPU 50.9~59.4%), 이는 ramp 잔류가 아니라 경합이다. 30분 런이라면 블록 간 p50이 어긋나는 것으로 즉시 드러났을 상황이다.

→ **5분 블록끼리 p50을 비교하는 것 자체가 경합 탐지 수단이다.** 기본 티어 이상에서만 쓸 수 있다.

**무제한 모드**에서는 `Q`를 누른 시점이 트래픽 종료로 잡히고, 거기서 앞뒤 `Trim`분을 잘라낸 구간이 통계가 된다.

## 4. 설정 키

전체 주석은 `BenchmarkConfig.ini` 안에 있다. 여기서는 헷갈리기 쉬운 것만 다룬다.

### `[Analysis]`

```ini
Minutes = 30   ; 통계를 낼 구간 길이
Trim    = 5    ; 트래픽 시작 직후 / 종료 직전 제외 구간
```

통계 구간 = **트래픽 구간에서 앞뒤 `Trim`분을 뺀 나머지**다. 접속 ramp, 메모리풀 성장, 종료 구간을 평균에서 배제한다. 클라이언트가 끊긴 뒤 서버가 `IdleTimeout`을 세는 유휴 구간은 트래픽 구간 밖이므로 정의상 자동으로 빠진다.

`Trim × 2 >= Minutes`이면 설정 오류로 중단한다.

### `[Server] NagleEnabled`

**Nagle 알고리즘**은 작은 송신을 모아서 한 번에 보내는 TCP 최적화다. 대역폭에는 유리하지만 지연이 늘어난다. 이를 끄는 소켓 옵션이 `TCP_NODELAY`라서 **이름과 동작이 서로 반대**라 늘 헷갈린다.

| ini | TCP_NODELAY | 동작 |
|---|---|---|
| `NagleEnabled = true` | FALSE | 패킷을 모아서 전송. 대역폭 유리, 지연 증가 |
| `NagleEnabled = false` | TRUE | 즉시 전송. 지연 최소, 패킷 수 증가 |

ini는 **"Nagle을 켤 것인가"**를 묻는다. baseline은 `false`(즉시 전송)다.

> 참고: `NetServer::Start`의 `nagle` 인자는 실제로는 `TCP_NODELAY` 값이라 의미가 반대다. `main.cpp`에서 `BOOL noDelay = nagleEnabled ? FALSE : TRUE;`로 뒤집어 넘긴다. 인자명 정리는 별도 과제.

### `[Client] Mode`

- `Mode = 1` — 접속을 끝까지 유지. `LifetimeMin/Max`, `ReconnectMin/Max`는 **무시**되며, 0이 아니면 경고를 출력한다(중단은 아님).
- `Mode = 2` — 일정 시간 유지 후 끊고 재접속 반복. `Server.IdleTimeout`이 `Client.ReconnectMax`보다 커야 한다. 안 그러면 재접속 공백을 서버가 "트래픽 종료"로 오판한다. (위반 시 **경고만 출력**하고 진행하므로 직접 확인해야 한다.)

### `[Client] SendIntervalMin / Max`

세션당 송신 간격(ms). **값이 작을수록 부하가 커진다** — 단, 현재 구현에는 하한이 있다. [9. 알려진 한계](#9-알려진-한계) 참고.

### 서버·클라가 ini 한 파일을 공유한다

두 프로그램 모두 `[Server]`·`[Client]` **전 키를 읽는다.** 읽지 않은 키가 남으면 오타로 간주해 중단하기 때문이다. 키 하나를 추가하면 양쪽 `main.cpp`에서 모두 읽어야 한다.

### 설정 오류는 조용히 넘어가지 않는다

`Config`는 아래를 모두 **중단 사유**로 처리한다. 잘못된 조건으로 45분을 날리는 것보다 즉시 멈추는 게 낫다.

| 분류 | 예 |
|---|---|
| 파싱 | 섹션 미종료, 빈 섹션명, `=` 누락, 섹션 밖의 키, 빈 키, 빈 값, **중복 키** |
| 타입 | 정수가 아님, boolean이 아님(`true`/`false`/`1`/`0`만 허용) |
| 누락 | 필수 키 없음 (`missing required key`) |
| 오타 | 아무도 읽지 않은 키 (`unknown key(s) - check for typo`) |
| 값 검증 | `Trim×2 >= Minutes`, `MaxUser < ClientCount`, `Server.Port != Client.ServerPort` |

기본값으로 대체된 키는 요약 CSV의 `DefaultedKeys` 컬럼에 남는다. **baseline 런에서는 이 칸이 비어 있어야 한다.**

## 5. 결과 파일

```
Benchmark\
├─ {Label}_{YYYYMMDD}_{HHMMSS}_server_samples.csv   런마다 새 파일
├─ {Label}_{YYYYMMDD}_{HHMMSS}_client_samples.csv   런마다 새 파일
├─ server_summary.csv                               런마다 한 줄씩 append
└─ client_summary.csv                               런마다 한 줄씩 append
```

모두 UTF-8 BOM + 한글 병기 헤더라 Excel에서 바로 열린다.

### 5.1 샘플 CSV — 초당 1행

| 컬럼 | 의미 |
|---|---|
| `Timestamp`, `ElapsedSec` | 시각, 시작 후 경과 초 |
| `Connected` | 현재 접속 수 |
| `FreeSession` *(서버)* | 세션 풀 여유분. 고갈되면 접속 실패 |
| `ConnectTotal`, `DisconnectTotal` *(클라)* | 누적 접속·끊김 |
| `RecvTPS`, `SendTPS` | 샘플 구간의 패킷 수 |
| `RecvBytes`, `SendBytes` | 샘플 구간의 바이트 수 (TCP/IP 헤더 40B 포함 추정치) |
| `AcceptTPS` *(서버)* | 샘플 구간의 accept 수 |
| `RecvTotal` *(클라)* | 수신한 누적 패킷 수 |
| `VerifiedTotal` *(클라)* | 에코 내용까지 검증한 누적 패킷 수 |
| `PoolTotal`, `PoolUse`, `PoolFree` | 패킷 풀 전체/사용/여유 |
| `CpuProcess` | **이 프로세스**의 CPU (코어 수로 나눈 값. 12코어에서 100%면 전 코어 포화) |
| `CpuProcessor` | **머신 전체** CPU |
| `MemProcessMB` | 이 프로세스의 `Private Bytes` (MB, 소수점 1자리) |

구간 평균만으로 안 보이는 것(특정 시점의 급락, 계단식 메모리 증가)을 추적할 때 본다.

> **`*TPS`는 구간 속도, `*Total`은 누계 스냅샷이다.** 성질이 다르므로 **속도 컬럼을 합산해 누계와 비교하면 안 된다** — 샘플링 루프가 두 값을 읽는 시점이 미세하게 달라 런 끝에서 수백 개가 어긋나고, 이는 유실이 아니다.
>
> **정합성은 `RecvTotal`과 `VerifiedTotal`을 직접 비교한다.** 두 카운터는 `OnRecv` 안에서 나란히 증가하므로 항상 같아야 하고, 다르면 패킷 타입 불일치다.

### 5.2 요약 CSV — 런당 1행

`Label` / `StartTime` / `Valid` / `Cfg*`(재현에 필요한 설정) / 통계 / 자원 사용 / `DefaultedKeys` 순. 런을 거듭하며 **같은 파일에 누적**되므로 그대로 열어 행끼리 비교하면 된다.

> **컬럼 구성을 바꾸면 기존 파일을 `server_summary_v1.csv` 식으로 rename하고 새로 시작할 것.** append 방식이라 헤더가 섞이면 Excel에서 열이 어긋난다.

## 6. 수치 읽는 법

### 6.1 백분위 (p5 / p50 / p95)

백분위는 **평균이 아니라 정렬했을 때의 위치값**이다. 초당 샘플을 전부 정렬한 뒤 nearest-rank(`index = ceil(p × N) - 1`)로 뽑는다.

- `p50` — 중앙값. 샘플의 절반이 이 값 이상
- `p95` — 상위 5% 경계. 전체의 5%만 이보다 높음
- `p5` — 하위 5% 경계. 전체의 5%만 이보다 낮음

**처리량은 지연 시간과 방향이 반대다.** 지연은 p95가 "최악의 경우"지만, **처리량은 p95가 "가장 잘 나온 초"**이고 **p5가 "가장 안 나온 초"**다. 그래서 둘을 같이 봐야 원인이 갈린다.

| 변화 | 해석 |
|---|---|
| p95가 떨어짐 | **상한 자체가 낮아짐.** 라이브러리 회귀를 의심할 1순위 신호 |
| p95는 그대로, p50/p5만 떨어짐 | 상한은 유지되는데 그만큼 못 낸 초가 늘어난 것 → 머신 경합·일시적 간섭 쪽 |
| p5~p95 폭이 넓어짐 | 안정성 저하. 스케줄링·GC성 일시 정지·락 경합 등 |

### 6.2 측정 유효성 — `CpuProcessor_avg`를 먼저 본다

머신 전체 CPU 평균이다. **이 값이 평소보다 높은 런은 수치가 아니라 머신을 측정한 것이므로 폐기한다.**

실측 기준선: 정상 런 **42~46%**, 다른 프로세스와 경합한 런 **55%**. 경합 런(2026-08-12)의 p50은 55821로, 같은 티어의 조용한 런(64020) 대비 **12.8% 낮았다.**

**보조 수단 — 블록 간 교차 확인.** 통계 구간을 5분 블록으로 나눠 p50을 비교한다. baseline 런은 6개 블록이 65973~65980(0.01%)으로 일치했다. 블록 하나만 처지면 그 시간대에 간섭이 있었던 것이고, 전 블록이 고르게 낮으면 런 전체가 경합 상태였던 것이다.

### 6.3 `Cpu_avg`가 사실상의 주 지표다

현재 부하 수준에서 **처리량은 라이브러리 성능이 아니라 송신 cadence가 결정한다**([9.2](#92-부하-수준이-타이머-분해능에-묶여-있다)). 서버 `Cpu_avg`가 15%(12코어 기준 약 1.8코어)로 포화와 거리가 멀다.

따라서 핫패스 회귀는 `RecvTPS`가 아니라 **`Cpu_avg`에 먼저 나타난다.** 같은 부하를 처리하는 데 CPU를 더 쓰게 되기 때문이다.

- `RecvTPS` — "의도한 부하가 실제로 걸렸는지" 확인용
- `Cpu_avg` — **같은 부하의 처리 비용. 모더나이제이션 전후 비교의 핵심**
- `p95` — 상한이 유지되는지

## 7. 런 유효성 체크리스트

요약 CSV의 새 행을 믿기 전에 확인한다.

1. **`Valid` = `OK`** — 아래 값은 모두 폐기 대상이다.
   | 값 | 뜻 |
   |---|---|
   | `INVALID(no connection)` | `IdleTimeout` 안에 아무도 접속하지 않음 |
   | `INVALID(window too short)` | 통계 구간이 비었음. `Q`로 일찍 중단한 경우 포함 |
   | `INVALID(max duration)` | 안전 상한 도달. 무언가 멈춤 |

   `INVALID` 행은 `WindowEndSec`가 음수로 찍힐 수 있다. 정상이며 무시하면 된다.

2. **`DefaultedKeys`가 비어 있을 것** — 비어 있지 않으면 ini의 키 이름이 깨졌거나 누락된 것이다.

3. **`WindowSamples`가 구간 길이와 맞을 것** — 30분 구간이면 1760~1800 정도. 크게 모자라면 샘플러가 굶은 것이므로 머신 상태를 의심한다. (약 1.8% 모자란 것은 정상이다. [9.1](#91-tps의-시간축이-1초가-아니라-약-1018초) 참고.)

4. **`Connected_min`이 설정한 `ClientCount`와 같을 것** (Mode 1) — 중간에 끊긴 세션이 있으면 작아진다.

5. **`CpuProcessor_avg`가 평소 범위일 것** (6.2 참고).

6. **행이 아예 없으면 크래시다.** 주기적 flush를 하지 않으므로 정상 종료 때만 기록된다. 이때는 실행 파일 폴더의 `Dump_*.dmp`를 확인한다.

## 8. 메모리와 풀 판독

### 8.1 `Mem_slopeMBperHour`의 해상도 한계

메모리는 0.1MB 단위로 기록된다. 짧은 구간에서는 **기록 해상도 자체가 시간당으로 증폭**된다.

| 구간 | 0.1MB가 환산되는 값 | 유의미한 최소 기울기 |
|---|---|---|
| 5분 | 1.2 MB/h | 읽지 말 것 |
| 30분 | 0.2 MB/h | 약 2 MB/h 이상 |
| 60분 | 0.1 MB/h | 약 1 MB/h 이상 |

누수 판단은 **확장(60분) 티어에서, 여러 런의 추세로** 한다. 30분 런 하나의 기울기로 단정하지 않는다.

### 8.2 서버 메모리는 부하가 아니라 `MaxUser`에 비례한다

`Session` 하나가 `SendBuffer[1000]`(포인터 8KB) + `RecvQ{4096}`을 들고 있어 약 13KB다. 서버는 이를 **`MaxUser`개만큼 시작 시 선할당**한다.

```
MaxUser 32000 × 약 13KB = 약 416MB
```

baseline 런의 서버 메모리 418MB가 여기서 나온다. 클라이언트는 `ClientCount`(2000)만 잡으므로(약 26MB + 프로세스 기본 사용량) 39MB 수준이다. **`MaxUser`가 다른 런끼리 메모리를 비교하는 것은 의미가 없다.**

### 8.3 패킷 풀

`Pool_end`(종료 시 풀 크기)가 **런을 거듭하며 계속 커지면** 패킷 반납 누락을 의심한다. 한 런 안에서 `Pool_max`까지 커졌다가 `Pool_end`로 줄어드는 것은 정상이다 — 피크 부하에 맞춰 풀이 자라고, 반납된 노드가 여유분으로 남는 구조다.

## 9. 알려진 한계

하네스 수치를 해석할 때 반드시 알아야 할 두 가지. 둘 다 **같은 머신에서 런끼리 비교하는 용도에는 영향이 없어** 현재는 그대로 두기로 했다.

### 9.1 TPS의 시간축이 1초가 아니라 약 1.018초

`NetServer::GetTransmit` / `NetClient::GetTransmit`은 `exchange(0)`으로 **읽으면서 리셋하는 누적 카운터**다. 즉 반환값은 "직전 호출 이후의 개수"이지 초당 비율이 아니며, **시간축은 호출하는 쪽의 책임**이다.

측정 루프는 `Sleep(1000)` + PDH 갱신 + `printf`로 구성되어 실제 주기가 **약 1.018초**다. 따라서 CSV의 `RecvTPS`/`SendTPS`는 **참값보다 약 1.75% 높다.** `RecvBytes`/`SendBytes`/`AcceptTPS`도 같은 누적-리셋 방식이라 동일하게 적용된다.

근거 (2026-10-16 baseline 런):
- 클라이언트 전 구간 `sum(RecvTPS)` = 154,568,026, `VerifiedTotal` = 154,570,000 → **비율 0.99999.** 카운트 누락은 없고 나누는 시간만 다르다
- `ElapsedSec`가 2씩 건너뛴 행이 2359행 중 42개(1.78%). 그 행들의 TPS가 2배가 아니라 정상값이다 → 실제 2초 공백이 아니라 **1.018초가 누적되어 정수 절삭이 한 칸 밀린 것**

참 처리량은 `구간 패킷 합 / 구간 벽시계 초`로 구한다. baseline 런은 `116,064,071 / 1800` = **약 64,480 pkt/s**.

**백분위 폭의 상당 부분도 처리량 변동이 아니라 루프 주기 흔들림이다.** p5 64010은 약 0.993초짜리 샘플에, p95 67968은 약 1.054초짜리 샘플에 해당한다. 최댓값 82002는 약 1.27초로 늘어진 샘플 하나이며, 서버와 클라이언트가 같은 순간을 잡았다.

> **왜 그대로 두는가**: 이 편향은 같은 머신·같은 빌드에서 상수이므로 런끼리 비교에는 영향이 없다. 다만 `printf`와 PDH 소요 시간에 좌우되므로 **다른 머신이나 다른 빌드 구성의 절대값과 비교할 때는 성립하지 않는다.** 보정하려면 샘플마다 실측 경과 시간으로 나눠야 하고, 이때 `GetTickCount`(분해능 15.6ms)는 쓸 수 없다 — 1초 구간에서 ±1.5% 노이즈가 생겨 제거하려는 편향과 크기가 같다. `std::chrono::steady_clock`을 써야 한다.

### 9.2 부하 수준이 타이머 분해능에 묶여 있다

`SenderThread`는 전 세션을 한 번 훑고 `Sleep(10)`을 호출하는데, 프로젝트 어디에서도 `timeBeginPeriod`를 부르지 않는다. Windows 기본 타이머 분해능은 **15.6ms**다. 송신 조건 판정에 쓰는 `GetTickCount`도 같은 분해능이다.

그 결과 **세션당 약 31ms(= 15.6ms × 2)에 한 번** 송신하며, `SendIntervalMin=1, Max=5` 설정은 분해능 아래라 사실상 무시된다.

근거 (baseline 런 통계 구간 1769샘플, `SendTPS ÷ 2000`):

| 세션당 송신 횟수 | 비율 |
|---|---|
| 32회 | 65.9% |
| 33회 | 31.1% |
| 그 외 | 3.0% |

97%가 정확히 32 또는 33회이고, `66000`·`64000` 같은 값이 반복해 찍힌다. 설정대로 평균 3ms였다면 초당 약 66만이 나와야 하는데 실제는 약 6.4만이다.

**의미**:
- 현재 부하에서 **라이브러리는 포화 상태가 아니다** (서버 `Cpu_avg` 15%). 처리량 수치는 라이브러리 상한이 아니라 송신 cadence를 반영한다
- 따라서 **핫패스 회귀는 `Cpu_avg`로 본다** (6.3 참고)
- 역설적으로 **재현성은 이 덕분에 최상이다.** 타이머 틱에 고정된 정속 부하라 런마다 같은 부하가 걸리고, 서버와 클라이언트 측정이 0.002%까지 일치한다
- `SendIntervalMin/Max`로 부하를 실제로 바꾸려면 **16ms 이상**의 값이어야 한다

라이브러리를 포화시키는 "부하 티어"는 `timeBeginPeriod(1)` 도입이 필요하며, 시스템 전역 타이머를 건드리고 baseline을 새로 잡아야 하므로 별도 과제로 둔다.

## 10. 운용 지침

1. **조건을 바꾸면 `Label`을 바꾼다.** 요약 CSV에서 행을 구분하는 유일한 수단이다.
2. **3회 돌려 중앙값을 비교한다.** 1회 수치로 몇 % 차이를 논하지 않는다. `CpuProcessor_avg`가 높은 런은 폐기하고 다시 돌린다.
3. **비교 대상은 같은 티어끼리.** smoke 수치는 기본·확장 티어와 비교하지 않는다.
4. **리팩토링 전후 비교 순서** — 변경 전 기본 티어 3회 → 변경 → 3회. 중앙값으로 `Cpu_avg`와 `p95`를 본다.
5. **`Benchmark\`는 `.gitignore` 대상이다.** 보존할 결과는 별도로 옮긴다.
